# omlx-demo

[oMLX](https://github.com/jundot/omlx) と [llama.cpp](https://github.com/ggml-org/llama.cpp) の推論速度を、同じモデルで比べるベンチマーク Web アプリです（Next.js）。両方のサーバに OpenAI 互換 API で同じリクエストを送り、ストリーミング応答から速度を計測します。

## 調査結果の要約

### MacBook Air（1人で使う想定）

MacBook Air（Apple M5・32GB）で、Gemma 4 12B（oMLX は MLX 4bit、llama.cpp は GGUF Q4_K_M）を使って比べました。

| 項目 | 結果 |
| --- | --- |
| 長いプロンプト（約4,400トークン）の処理 | oMLX が約1.3倍速い |
| 生成速度（1本だけのとき） | 同程度 |
| 同時4リクエストの合計スループット | 同程度 |
| 同じ文書を2回目に送ったときの応答 | llama.cpp が速い |

- 長い文書やコードを毎回渡す用途では oMLX が有利です。短い対話が中心なら、大きな差はありません。
- ファンのない機種では、続けて測ると熱で速度が落ちます。計測順を入れ替えて測り、先に測った値どうしで比べています。
- 32GB の Mac で 12B クラスのモデルを2つのサーバに同時に載せると、oMLX のメモリガードによって長いプロンプトが失敗することがあります。計測は片方ずつ行ってください。

### Mac Studio（複数人で使う共有サーバの想定）

Mac Studio（Apple M4 Max・36GB）で、同じモデルを使って比べました。会社で複数人が1台のサーバに接続する使い方を想定し、同時8本・16本と混在負荷（長文の要約2本の処理中に短い質問6本）も測っています。oMLX は 0.7.3 です。llama.cpp は、同時実行と混在負荷の項目が build 12359、それ以外（1本だけ・長いプロンプト・2回目）が build 9590 での値です。多人数シナリオでは、両サーバとも同時処理数を16にしています。

| 項目 | 結果 |
| --- | --- |
| 生成速度（1本だけのとき） | oMLX が約1.2倍速い |
| 長いプロンプト（約4,400トークン）の処理 | 同程度 |
| 同じ文書を2回目に送ったときの応答 | llama.cpp が約4倍速い |
| 同時2本 / 4本の合計スループット | oMLX が約1.6倍 / 約1.2倍 |
| 同時8本の合計スループット | 同程度 |
| 同時16本の合計スループット | llama.cpp が約1.1倍 |
| 同時8本・16本で最初のトークンが返るまで（p95） | llama.cpp が約1.4〜1.7倍速い |
| 混在負荷で短い質問の最初のトークンが返るまで | oMLX が約1.5倍速い（約15秒、llama.cpp は約22秒） |

- 同時に使う人が少ないうちは oMLX が速く、人数が増えると llama.cpp が追いつき、16人では上回ります。
- 長文の要約が混ざると、どちらのサーバでも短い質問が15秒以上待たされます。長文の処理を別のサーバに分けるなどの対策を検討してください。
- **llama.cpp の版で結果が大きく変わります。** 古い版（build 9590）では同時2〜8本の合計スループットが約47 tok/s から伸びず（1本だけのときとほぼ同じ）、oMLX が同時8本で約3.8倍速いという結果になりました。新しい版（build 12359）では同時8本で 164 tok/s に伸びています。複数人で使う場合は、llama.cpp を新しい版にしてください。
- GGUF は MacBook Air とは別のファイル（同じ Q4_K_M）です。1本だけのときの値は、MacBook Air の結果と単純には比べられません。

数値は特定の機種・設定での結果です。環境が変われば結果も変わります。

## 必要な環境

- Apple Silicon の Mac（oMLX は macOS 15 以上）
- Node.js 20.9 以上
- oMLX（例: `http://127.0.0.1:8000`）と llama-server（例: `http://127.0.0.1:8080`）が起動していること
  - どちらか片方だけでも動きます。接続できたサーバだけを計測します。

## 使い方

```bash
npm install
npm run dev
```

http://localhost:3000 を開き、「全シナリオを計測」を押します。結果は画面に表示され、`bench-results/results.jsonl` にも追記されます。

### 接続先の設定

接続先はサーバ側の環境変数で決まります（`.env.local` に書けます）。ブラウザから接続先を変えることはできません。

| 変数 | 既定値 |
| --- | --- |
| `OMLX_BASE_URL` | `http://127.0.0.1:8000/v1` |
| `OMLX_MODEL` | `gemma-4-12B-it-4bit` |
| `OMLX_API_KEY` | なし |
| `OMLX_MAX_CONCURRENT_REQUESTS` | `8`（oMLX の既定値。同時処理数の警告に使用） |
| `LLAMACPP_BASE_URL` | `http://127.0.0.1:8080/v1` |
| `LLAMACPP_MODEL` | `gemma-4-12b-it-Q4_K_M.gguf` |
| `LLAMACPP_API_KEY` | なし |
| `BENCH_ALLOWED_HOSTS` | なし（`localhost` / `127.0.0.1` / `[::1]` 以外のホスト名を許可する場合にカンマ区切りで指定） |

### 計測シナリオ

| シナリオ | 内容 |
| --- | --- |
| 短いプロンプト | 約30トークンの質問に回答 |
| 長いプロンプト（初回） | 約4,000トークンの文書を要約 |
| 長いプロンプト（2回目） | 直前と同じ文書に別の質問（プレフィックスキャッシュの効果） |
| 同時2リクエスト / 同時4リクエスト | 短いプロンプトを同時に送信 |
| 同時8リクエスト / 同時16リクエスト | 短いプロンプトを同時に送信（複数人での利用を想定） |
| 混在負荷 | 長文の要約2本の0.5秒後に短い質問6本を送信（長文の処理中に短い質問がどれだけ待たされるか） |

- 温度 0、出力は `ignore_eos` で毎回 256 トークンに固定します。
- 毎回プロンプトの先頭に一意の ID を入れ、前の計測のキャッシュが効かないようにしています。
- 同時リクエスト数がサーバの同時処理数を超える場合は、画面に警告が出ます（llama-server は `--parallel`、oMLX は `--max-concurrent-requests` で設定）。
- llama-server は `--parallel N` を指定すると、KV キャッシュを各スロットに `-c` の N 分の1ずつ分けます。同時16本で長いプロンプトを扱う場合は、`--kv-unified` で KV を共有させてください。

### 別の Mac で同じ条件の計測をする

`scripts/run-bench.sh` が、推論サーバを片方ずつ起動して両方の計測順で全シナリオを測り、比較表（`summary.md`）まで作ります。準備と手順は [docs/benchmark-runbook.md](docs/benchmark-runbook.md) を参照してください。

## セキュリティ

ローカルでの計測用です。API は `localhost` 系のホストと同一オリジンからのリクエストだけを受け付けます。ただし `next dev` はすべてのネットワークインターフェースで待ち受けるため、LAN 内から直接アクセスされることを防ぎたい場合は `npx next dev -H 127.0.0.1` で起動してください。
